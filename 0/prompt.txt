**`tools/content_lang_keys.py`** (already read in full) is the established migration tool and **already explicitly excludes `presets.json`** with a comment block (lines 30-36) matching the prompt's memory verbatim, plus a `ponytail:` marker: *"12 clases y 12 subclases siguen en espanol; el arreglo es desacoplar guardado de display."* This confirms the architecture is understood but intentionally deferred — this plan's Phase 6 is that deferred work.

**`ContentNames.of(name)` / `.plain(name)`** (`src/main/java/net/hawthorn/dndsheets/ContentNames.java`): treats the stored string as a translation key via `Component.translatable(name)`, falling back to literal display if the key doesn't resolve (Minecraft's own behavior for missing keys) — this is *exactly* the mechanism needed for Phase 6, and it already has a documented, accepted limitation (`ContentNames.plain`, used by `CombatManager.java:642` for weapon-buff roll formulas and `TurnManager.java:567` for the turn-tracker label) that resolves in the **server's** locale because the destination is a raw `String`. This is **pre-existing and out of scope** — not something Phase 6 needs to fix, just not to make worse.

**Self-tests already have partial coverage, with known gaps documented in their own source:**
- `checkChatMessagesAreTranslatable` (`JsonContentSelfTest.java:3460-3557`) already fails the build on (a) `sendSystemMessage(Component.literal("...`, (b) any `Component.literal("...")` containing prose (`[a-z] [a-z]` pattern) **outside** `/command/` files, (c) `setHoverName(Component.literal("...` (item names baked into NBT). It **currently tolerates** prose literals inside `/command/*.java` files up to a hard cap: `assertTrue(enComandos &lt;= 86, ...)` with its own `ponytail:` comment: *"86 respuestas de comando siguen en espanol fijo... bajarlo a 0 es la tanda que falta."* — **this is exactly Category 2's DM/command feedback work**, and the plan must lower this cap as that work lands, not just translate the strings.
- There's also an `*Overlay.java`-specific check (`JsonContentSelfTest.java:3528-3555`) that scans `TurnHudOverlay`/`ResourceHudOverlay` for **any** accented character or lowercase-space prose outside comments — already passing today, confirming those two files have no currently-failing literal (any Spanish text the Explore agents found there is either in comments, or ASCII-only single words like `"nivel"`/`"cantidad"` that slip both this regex and the general one, since neither requires an accent+space together for single-word ASCII strings). **No lint currently covers bare ASCII Spanish words** (`nivel`, `cantidad`, `tipo`, etc.) or Java comments or enum `label()` bodies — those need a manual grep sweep, not an existing gate.
- `checkContentNamesAreTranslated` (`JsonContentSelfTest.java:3398-3458`) is the established pattern for content-name-as-key: it greps `defaults/*.json` for `content.dndsheets.*` keys and asserts both `en_us.json`/`es_es.json` have them, **and** greps Java source for any place a `.name()/.label()/.displayName()` accessor feeds a `Component`, `setHoverName`, `setCustomName`, `addRow`, or string concatenation without going through `ContentNames.of/.plain` first (with an `i18n-ok` escape-hatch comment for pre-resolved cases, as used in `GrimoireScreen.java:169`). **Phase 6 should extend this same check** rather than invent a new one, once `presets.json` gets keys.

**The enum "canonical Spanish key with separate `label()`" pattern is confirmed but not uniform** — this matters for Phase 5 sequencing:
- `MagicSchool` (`MagicSchool.java`): enum constants are English (`EVOCATION`), backing `key` field is Spanish (`"evocacion"`), `label()` returns accented Spanish (`"evocación"`) for 5 of 9 values, falls through to `key` for the rest. Used at `SpellRegistry.java:226` writing straight into pack JSON output.
- `CreatureType` (`CreatureType.java`): identical shape — English constants, Spanish `key`, Spanish `label()` override for 4 of 15. Used at `MonsterRegistry.java:348`.
- `CreatureSize` (`CreatureSize.java`): English constants, Spanish `key`, but **`label()` just returns `key`** directly (no separate label logic) — used at `MonsterRegistry.java:349`.
- `DamageTypes` (`DamageTypes.java`): **not an enum at all** — a `String[] CANONICAL` of Spanish words plus an `ENGLISH` alias `Map` for `normalize()`. **There is no `label()` method to fix here** — nothing currently paints a `DamageTypes` value directly; `multiplierForLabel` only consumes `resistant`/`vulnerable`/`immune` (already English). Whatever displays a damage type today does so from the raw JSON string the DM wrote, not from this class. This one may need **no code change**, only a check of paint sites that print `damageAffinities` keys raw (worth a grep, not a redesign).
- `Condition` (`Condition.java`): **the deepest one** — the enum constants **themselves** are Spanish (`CEGADO, HECHIZADO, ENSORDECIDO...`) and `label()` is just `name().toLowerCase()` — there is no separate internal-key/display-label split at all. This label is **not purely a display string**: it's serialized into the sheet's `"conditions"` JSON array (`Combatant.java:406-426`), sent over the network (`ConditionListScreen.java:67`, `network/BrowseActionMessage.java:517`, `SheetSummaryRequestMessage.java:57`), and parsed back via `Condition.fromLabel(String)` (`Combatant.java:674`, `SheetCommand.java:302`, `TurnManager.java:836,852`, `ConditionListScreen.java:41`). **Renaming the enum constants (or what `label()` returns) is a persistence-format change**, not a pure display fix — this needs its own careful sub-step (see Phase 5).

**Species submodule (Category 4) — two parallel, unrelated systems, confirmed by reading the code:**
1. The **data-driven Origins integration** (`species/.../resources/data/...` origin layer JSON + `dndsheets_species/lang/en_us.json`'s `origin.dndsheets_species.&lt;id&gt;.name`/`.description` keys, already 100% English, full 8-language set exists). This is the **primary** path when the Origins mod is installed (`CharacterOptionListScreen.java:18-19`: *"Con el addon species instalado este selector no se usa (Origins elige y el addon escribe la hoja)"*).
2. `RaceRegistry.java`, `BackgroundRegistry.java`, `DndsheetsSpeciesMod.java`'s `trait(id, name)` calls — Java-hardcoded Spanish display names, used **only** as the **fallback** in-mod picker (`CharacterOptionListScreen`) when Origins isn't driving selection. These names are read as raw `List&lt;String&gt;` and displayed with no translation-key indirection at all today — a completely separate, much simpler code path than #1.

Given the fallback path was deliberately kept as plain hardcoded strings (not routed through the lang system), and per the ladder ("does this need new infra?"), the lazy-correct fix is to **swap the Spanish literals for English literals in place** in these three files, not build a parallel key system for a path that was never keyed — that would be new infrastructure for a fallback picker, not requested. Flag as a documented simplification (`ponytail:` comment) that this fallback path stays single-language (English) while the primary Origins path keeps its full multi-language support.

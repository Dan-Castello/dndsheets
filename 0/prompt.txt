## 2. Server echoes put a stale copy behind the new screen

Many `open()` methods use `Minecraft.getInstance().screen` as the parent. When the server re-sends a list after an action, the form has already gone back to the old list. The new list then gets the **old copy of itself** as its parent.

Four screens already guard against this: `ContentEntryListScreen.open` (44-49), `OptionsManageScreen.open` (36-38), `ConfigListScreen.open` (32), `RulesScreen.open` (34). The guard is:
```java
Screen parent = current instanceof X stale &amp;&amp; &lt;same key&gt; ? stale.parent : current;
```

Places where it's missing or broken:

| Where | What happens now | Should go |
|---|---|---|
| `dungeon\...\DungeonPieceListScreen.java:38-40` | After an edit, capture, delete or trace save, the echo comes from `DungeonPieceUpdate/Capture/Remove/TraceCaptureMessage` (60, 63, 43, 378). The new list's parent is the old list. Back shows the stale list (deleted piece still there), then Back again reaches the DM Panel. | Use the same stale-parent guard |
| `...\client\gui\TraitEditScreen.java:85-88` `save()` → `open(updated)` (39-41) | Saving from `TraitBasicInfoScreen` or `TierAddScreen` opens the new trait editor with the **form** as parent. The server echo (`ContentEntrySaveMessage:73`) then sees a `TraitEditScreen` on screen, so the guard misses and a list opens on top with the editor as parent. You get pushed into the list.

# Project context — dndsheets

Deep-dive reference for anyone (human or AI) picking up this codebase cold. It used to carry a full
narrative log of every bug fixed and every roadmap decision made, in essay form — that made it the single largest file in the repo and unreadable as
a map. It has been purged: the log below states symptom → cause → fix in one or two lines each: the
code, the self-tests and `git log` are the source of truth for the story, this file is the index.

## What this is

A Minecraft Forge mod (**1.20.1**, Forge `47.2.0`/`47.4.10`/`47.4.22` for dev tooling, mod id
`dndsheets`) that turns Minecraft into a D&D 5e VTT: a fillable character sheet bound to a keypress,
real 5e combat resolution layered on top of vanilla PvP/mob combat (opt-in per weapon/monster/spell
— anything unconfigured behaves like normal Minecraft), and a full DM toolkit (spawn monsters with
real stat blocks, run initiative, generate dungeons from vanilla's jigsaw system, create content
in-game). It needs to be installed on both client and server. It is now three Gradle modules — the
core (`dndsheets`) plus two hard-dependent addons, `dungeon` and `species` — see "Modularity Map"
below. It targets 1.20.1 today and **the door to future Minecraft versions is deliberately left
open** — see "Portability to future Minecraft versions". Other tabletop systems are out of scope.

## Invariants — break these and it fails silently

Every one of these has already cost someone a debugging session, or would. Read this list before
your first edit. The numbering is load-bearing: code comments cite these by number.

1. **Never reorder or delete an entry in `DndsheetsMod.registerNetworkMessages`.** *Machine-enforced:*
   `JsonContentSelfTest.checkNetworkShape` pins `NETWORK_SHAPE`/`NETWORK_ORDER`/`NETWORK_WIRE` against
   the source. Message id = registration order; an insertion silently renumbers everything after it.
   Add new entries at the end.
2. **Never insert a constant into the middle of an enum that crosses the network.**
   `FriendlyByteBuf.writeEnum`/`readEnum` travel by ordinal. `SheetAdjustMessage.Field` is the live
   example; `CONDITION` is last for exactly this reason.
3. **Prefer extending a parameterized message over registering a new class.** `SheetAdjustMessage`
   already merges six former message classes behind a `Field` enum; bulk "give one of N similar
   things" flows follow the same shape.
4. **Anything that mutates a sheet must reach `SheetLoader.saveServer`.** *Machine-enforced:*
   `JsonContentSelfTest.checkSheetWritesArePersisted` fails the build when a file mutates a sheet with
   a `ServerPlayer` in hand and never saves. Use `SheetLoader.saveAndSync(player, sheet)` — persists
   and syncs in one call. The 5-minute autosave is a backstop, not the write path.
5. **`/reload` can never publish a new or edited dungeon pool in the same session.**
   `Registries.TEMPLATE_POOL` is worldgen; it loads with the world. Tell the DM to re-enter the world.
6. **A dungeon start pool must contain only pieces that have the start jigsaw.** Vanilla picks one
   random piece from the pool and searches only inside it, never retrying. Mixed pools fail
   non-deterministically.
7. **Never hand-roll a screen's layout: extend one of the four bases.** `FormPanelScreen` (parchment
   panel, frame, title, rule, `Math.max(44, ...)` floor, `addFieldRow(...)`); `SmallFormScreen`
   (Confirm/Cancel/Delete on top of it); `ListPickerScreen` (scrollable row list); `ModalDialogScreen`
   (fixed-size dialog). **No concrete screen extends bare `Screen`.** The worst layout bugs in the
   project's history came from the one screen that used to (see bug #2 below).
8. **Content JSON is user data.** Adding a field is fine; renaming or requiring one breaks every pack
   a DM already wrote. Every parser defaults missing fields and isolates errors per element.
9. **Leave vanilla alone when nothing is configured.** An unregistered weapon, a mob with no stat
   block, a player with no sheet — all must behave exactly like normal Minecraft.
10. **Content JSON is formatted by hand, compactly.** Never rewrite these files with a `json.dump` —
    it reflows everything and makes the diff unreadable. Insert respecting the style.
11. **Every non-trivial rule gets a case in `JsonContentSelfTest`.** Runs on `gradlew build`, no Forge
    runtime needed. Logic that can't be reached without a running game goes behind a pure helper
    class that can (`CharacterRules`, `SpellSlots`, `Cover`, `Condition`, `AttackRules`/`SaveRules`,
    `CreatureType`/`CreatureSize` — see "Portability" below for why that split also pays for the port).
    **What really requires a world goes to `runGameTestServer`**, not to the self-test: real entities, their
    persistent NBT, the link between the rules and the game. `./gradlew runGameTestServer` starts a
    server, places `dndsheets:arena` (generated by `tools/make_gametest_arena.py` — the format is binary
    NBT, it is not written by hand) and exits with the number of failures as the exit code. See
    `gametest/CombatantGameTests`. Split rule: if it can be checked without starting the game, it goes in the
    self-test, which takes a second instead of a minute.

## Content vocabulary is English (legacy Spanish still reads)

Every value the engine compares — damage types (`fire`, `slashing`...), conditions (`prone`, `paralyzed`...),
creature types/sizes/schools (`undead`, `gargantuan`, `evocation`), advantage labels, warlock pacts
(`chain`/`blade`/`tome`), encounter ratings, trait ids (`monk:martial_arts`) — is written in English on disk,
on the network and in the packs. Saves and packs written when these were Spanish keep working, because each
reader accepts the old spelling and maps it to the English one (`DamageTypes.normalize`, `Condition.fromLabel`,
`CreatureType`/`CreatureSize`/`MagicSchool.parse`, `DiceManager.advantageFromLabel`, `CombatManager.pactOf`,
`TraitRegistry.canonical`); `checkImportedContent` pins that. **Write new values in English, and never remove a
legacy alias** — that is what keeps old sheets alive (invariant 8). The Spanish language files (`es_*`) only
translate what the player reads; they never carry vocabulary the engine compares.

## Modularity Map

Three Gradle modules, one repo: the core (`dndsheets`) and two addons, `dungeon` and `species`. Each
addon is a **hard dependency on the core**, not an independent mod — it compiles against the root
project's source set (`implementation project(':')`), not a published jar, so a change in either
module is visible without building the other first.

- **`dungeon`** (`dndsheets_dungeon`) owns the jigsaw/structure toolkit: `DungeonManager`,
  `DungeonPieceRegistry`, `DungeonToolManager`, `EncounterPopulator`, `GridToStructure`, the
  trace/capture subsystem (`DungeonTraceScreen`/`DungeonTraceCaptureMessage`/
  `DungeonTracePreviewRenderer`/`DungeonPiecePlacer`, ~1.000 LOC: capture a build by marking
  two corners in the world), plus its own GUI/command/network packages. It reaches into the core for
  `DndsheetsMod.LOGGER`/`PRETTY_GSON`/`MODID`, `DndPaths`, the shared GUI bases (`SmallFormScreen`/
  `ListPickerScreen`/`ModalDialogScreen`/`GuiStyle`/`TomeButton`), `network.NetworkUtil` (the DM
  permission guard, once per message), `MonsterRegistry`, `SheetLoader` and `InteractionEvents` — it
  does not duplicate any of them.
- **`species`** (`dndsheets_species`) bridges [Origins](https://github.com/apace100/origins-forge)
  (race/background selection) into this mod's rules: `RaceRegistry`, `BackgroundRegistry`,
  `OriginBridge`, `/dndspecies sync`. Origins is a **hard dependency of this addon only** — the core
  never references it. Origins picks the race; this addon applies the Ability Score Improvement and
  the SRD racial traits through the core's own write path (`SheetLoader`/
  `DndsheetsMod.sendSheetFieldUpdate`, invariant 4) — Origins never writes the sheet directly.
- **Why split at all, and why now:** the core was carrying two features (a full jigsaw dungeon
  generator, an Origins bridge) that are large, optional in spirit, and each pull in their own GUI
  surface. Splitting them out is what lets a pack ship the core without either, and lets each addon's
  pure logic (`DungeonManager.buildPoolJsons`/`GridToStructure`, `RaceRegistry.apply`) get its own
  `check`-wired self-test (`DungeonSelfTest`, `SpeciesSelfTest`) — same pattern as the core's
  `JsonContentSelfTest`, run with `./gradlew testDungeonSelf`/`testSpeciesSelf`, no Forge runtime.
- **Neither addon can be dev-tested loaded together with a mixin-based mod** (Origins/Apoli included)
  — see "Library Audit" for why `runClient` stays otherwise empty and what that means for testing
  `species` against the real Origins jar.

## Library Audit

What this mod actually links against, and how each was evaluated — since `dependencies/` holds jars
with no other paper trail:

- **dicebot** (`io.github.tfriedrichs:dicebot`) — hard dependency, shaded and relocated into the jar
  (`shadowJar`, package `net.hawthorn.dndsheets.relocated.dicebot`) so it never collides with another
  mod's copy.
- **Curios API**, **Patchouli** — soft dependencies. `compileOnly` against the `api` classifier only
  (the two or three methods actually called: `CuriosApi.getCuriosInventory`/`getEquippedCurios`,
  `PatchouliAPI.get()`), pinned to an early 5.x for Curios so the mod compiles against — and works
  with — whatever version a player has. `CuriosCompat`/`PatchouliCompat` contain **zero** references
  to the real types outside an `isLoaded()` guard (verified with `javap`), so a missing jar degrades
  to "no Curios slots" / "Guide opens as a written book" instead of `NoClassDefFoundError`.
- **Jade** — soft dependency, `compileOnly` from CurseMaven (`curse.maven:jade-324717:5072729`, the
  oldest 1.20.1 build, same "pin early" reasoning as Curios). Pointing at a creature shows its AC, HP
  and conditions on the HUD. **One class, `JadePlugin`, and no `isLoaded()` guard anywhere** — unlike
  Curios the call direction is reversed: nothing in this mod references that class, Jade loads it by
  scanning for `@WailaPlugin`, so with Jade absent nobody loads it and there is nothing to guard. It
  reads `Combatant` and computes nothing; `Combatant.of` returning null is invariant 9 applied to the
  HUD. *Gotcha, cost one build:* `exclusiveContent {}` does **not** work with `fg.deobf` + CurseMaven
  (it does work for the Modrinth maven in `species`) — use a plain `content { includeGroup }` filter.
- **Pehkui** — soft dependency, `compileOnly` from the Modrinth maven
  (`maven.modrinth:t5W7Jfwy:rUlbXz1h`, Pehkui 3.7.6). Draws each creature at the size its stat block
  declares. Two classes, the exact `CuriosCompat`/`CuriosSlots` shape, because here *we* call *it*.
  Backed by `CreatureSize` (the `CreatureType` mold: closed enum, accent/English-tolerant `parse`,
  `UNKNOWN` that never fires) and a new optional `size` field on `MonsterStatBlock`, filled for 329
  of the 330 shipped monsters from the SRD (the 330th, `fire_mage`, is not SRD). **Why it stopped
  being cosmetic:** 149 of those 330 are bigger than Medium — 102 Large, 32 Huge, 15 Gargantuan — and
  until now the only thing the mod could say about size was `appearance.baby`. Scale comes from 5e's
  grid space ÷ 5, so Small **is 1.0 on purpose**: it shares the Medium square, and shrinking it here
  would multiply with the `baby` flag the goblins already use. `checkCreatureSize` pins all of it,
  including that no shipped monster combines `baby` with a scaling size.
- **Origins + Apoli** — the `species` addon's hard dependency, `compileOnly`. Origins comes from the
  Modrinth maven (`maven.modrinth:jl3m2lR9:vynFXywM`), pinned by version id so a new Origins release
  cannot move under the build. **Apoli has no Maven coordinate of its own for Forge** (404 on
  Modrinth; on CurseForge it would have to be pinned separately and could drift) — and it needs none:
  it travels *inside* the Origins jar as `META-INF/jarjar/apoli-forge-*.jar`, and a nested jar is not
  on javac's classpath. `unpackApoli` extracts it from that same artifact, so the Apoli compiled
  against can never desynchronise from the Origins that ships it. Same isolation discipline as
  Curios: `OriginBridge` degrades gracefully if Origins is absent, but `species` itself is meaningless
  without it. *Gotcha:* Gradle 8 rejects `compileOnly configurations.x` — wire it with
  `compileOnly.extendsFrom`.
- **Caelus, Iron's Spellbooks, origins-classes, apoli_stream_leak** — evaluated and **not**
  integrated. Their jars (plus stale local copies of Curios/Patchouli, which now come from Maven as
  `compileOnly`) were deleted from `dependencies/`; this paragraph is the record of that evaluation.
  `dependencies/` itself is now gone: Origins was the last thing in it, and it resolves from a Maven.
  **Re-evaluated 2026-08-26 for the magic pass and rejected again, on purpose:** Iron's Spells was taken
  as an *architectural reference* (schools with their own identity, a visible wind-up before the effect,
  a spell window that is more than a list) and every one of those was reimplemented natively — see "El
  sistema de magia" below. Depending on it would have cost a mixin-based hard dependency that
  `runClient` cannot load here (same SRG/Parchment wall as everything else in this list), a licence that
  forbids redistributing its assets, and a mana-based engine competing with 5e spell slots. Nothing was
  copied from it: zero of its code, zero of its assets.
- **Why none of these run in `runClient`:** every one of them (plus Oculus, LionfishAPI, Citadel,
  tried the same way) mixes into vanilla classes using SRG names (`f_19803_`, `m_91087_`), and this
  dev environment runs Parchment mappings, where those names don't exist. `fg.deobf` fixes the jar's
  bytecode but not its mixins; forcing `mixin.env.remapRefMap` fixes that jar's mixins and breaks
  every other mixin mod in the same client. No combination works, so `runClient/mods` stays empty on
  purpose — these integrations are tested against a real `./gradlew build` install instead, and the
  structural isolation (`CuriosCompat`, `PatchouliCompat`, `OriginBridge`) is checked with `javap`
  rather than by running it.

## The rules core (read this before touching combat)

Three files carry the 5e rules layer; read them before assuming a pattern from an older file still
applies.

**`Combatant`** is the single abstraction over "anything that participates in 5e rules": a player
(backed by a `JsonObject` sheet) or a monster (backed by a `MonsterStatBlock` + entity NBT). Before
it existed, that split was a `boolean isMonster` and every rule needing "the target's AC" or "take N
hit points off it" was written twice — monsters had no resistances, no defensive reactions, no
concentration. `Combatant.of(entity)` returns null for anything outside the rules; callers fall back
to vanilla behaviour. Implementations hold no state of their own — they read/write where the state
already lived. Three implementations, and the two sheet-backed ones share `SheetBacked`:
`PlayerCombatant`, `NpcCombatant` (a character with a body, not a player behind it), `MonsterCombatant`.

**`Condition`** is the 14-condition table of 5e, one `switch` per rule rather than a positional
constructor. Storage is `label` or `label@sourceEntityId` in the sheet's JSON array / monster's NBT
string — the suffix is optional so pre-existing data still loads. `TurnManager.applyEffect` treats
any effect name that *is* a condition as one automatically — no new command, no new JSON field.
Three choke points enforce them: `TurnManager.tryAct` (can't act), `MovementAnchorTracker.enforceBudget`
(speed 0), `CombatManager.resolveAttack` (advantage/auto-crit). Charmed is checked at the attack entry
points instead, since it depends on *who* the target is.

**`CharacterRules`** holds "whose character is this" plus the max-HP formula — split out of
`SheetLoader` because `SheetLoader` resolves `FMLPaths.GAMEDIR` at class-init and can't load outside
a running Forge instance. `SheetLoader.sheets` is keyed by **character id**, not player UUID, with a
binding **derived** from an `active` field on each sheet (never a separate index that can drift out
of sync). A player UUID is still a valid character id, so pre-existing sheets need no migration.

**Known ceiling — one combat per server.** All of `TurnManager`'s state is static and single per
process (~18 fields), so only ONE turn-mode encounter can exist at a time on the whole
server. A deliberate decision (one server = one table): if two groups ever play simultaneous
encounters, that is per-encounter state and a big rewrite, not a patch. It is annotated with a
`ponytail:` comment in the class itself.

## The magic system

The rules were already there (modes, areas with real geometry, upcasting, concentration, counterspell,
slots per level); what was missing was everything that makes casting a spell **feel like something**. Pass of
2026-08-26.

- **`MagicSchool`** — the 8 schools of 5e, the exact same mold as `CreatureType` (an enum, a `parse`
  tolerant of accents/English/hyphens, an `UNKNOWN` that never filters or triggers anything). **It gates no
  rule**: it decides which particles and sound a spell is CAST with. Damage type already distinguished the
  impact, but half the SRD does no damage, and until now all 87 spells started with the same purple
  swirl. `CombatFx.FX_BY_SCHOOL` reuses the impacts' `HitFx`/`playCombo`, with no parallel
  structure. **Zero new assets**: everything is vanilla `ParticleTypes`/`SoundEvents`.
- **DIRECTED particles — the visual lever for everything else.** `sendParticles` with `count=0` does not
  scatter randomly inside a box: it sends ONE particle whose `dx/dy/dz` is its **velocity vector**.
  This whole class was painted with `count>0`, and that is exactly why every spell came out as a
  still little cloud — nothing moved in a particular direction. On top of `directed()` are built
  `burstRing` (shockwave), `burstShell` (a spherical shell spread with the golden angle, not by
  latitude/longitude, which piles half the points at the poles) and `basisFor`/`onCircle` (circles
  and helices around any direction, not just the world's axes).
  The four phases of a spell are now distinct from each other: **charge** (a two-armed helix whose radius
  SHRINKS —the opposite of an explosion— plus motes falling inward and a rising pitch), **cast**
  (a core that bursts + a conical jet where it is looking + three shockwave rings at the feet, which stay
  where it was cast and don't follow the caster), **travel** (a core with velocity + two helical strands) and
  **impact** (an expanding shell + a ring on the ground; passing the save is a shell that
  closes inward, that is, a shield). `CombatFx.shapeOutline` draws the cone and the line with the same
  geometry that `SpellCastManager.inShape` uses to decide who they reach: until now those two shapes
  **drew nothing at all**, neither on casting nor in the preview.
- **The order of the phases matters and it already broke once**: `CombatFx.spellCast` (the flash) lived in
  `prepare()`, that is, before the charge — with a casting time you saw burst → helix → impact,
  the sequence reversed. It lives in `resolve()`; an instant spell resolves on the same tick, so
  nothing changes for it.
- **`SpellCastManager` is split in two**: `prepare()` validates and **charges** (target, slot, turn,
  counterspell) and `resolve()` applies the effect, with a `CastRequest` in between. The cut is not
  aesthetic: it is what allows real time to pass between the two halves.
- **`CastingManager`** — spells that take time to go off. `castTicks` in the JSON, or derived from the level by
  `Config.castTicksPerLevel/castTicksMax`; **0 = the usual instant casting** and that is the way
  out (invariant 9). It is interrupted by damage (a CON save with **the same formula as
  concentration**, `max(10, damage/2)`, hooked into `ConcentrationManager.onDamageTaken` because it is the
  point all four damage paths already go through), by becoming incapacitated and by moving. The
  slot is lost anyway, as with counterspell. State in RAM, **never on the sheet**: a half-finished spell
  must not survive a restart, and that is why `notifyClient` sends the patch without touching the
  `JsonObject` (the invariant 4 self-test caught it, rightly).
- **`TurnManager.holdAutoAdvance`/`resumeAutoAdvance`** — without this the turn passed in the middle of the
  cast and the spell resolved on someone else's turn. It reuses `undoAction`'s `turnToken++`.
- **Animation: first person only, and it is a decision.** `client/SpellCastAnimator` moves the hand through
  `RenderHandEvent`. The third-person pose would require writing to `HumanoidModel.rightArmPose`, which
  `PlayerRenderer.setModelProperties` rewrites **after** `RenderPlayerEvent.Pre` — without a mixin there is
  nowhere to hook in, and mixins don't come in here. What others see is the particle charge of
  `CombatFx.spellCharge`, which is server-side.
- **Slot spending is ANNOUNCED.** It used to be deducted silently and the only trace was a HUD number
  going down; with a cantrip —which by rule spends nothing— the reasonable conclusion from outside is "this
  ignores spell slots". Now the level spent and what remains of that level are named, and a
  cantrip explicitly says it is at will. Reported as-is while playing.
- **Spell preparation** — `"prepared"` per entry in `sheet.spells[]`, limit
  `CharacterRules.preparedLimitFor` (the class ability's modifier + level, minimum 1; 0 turns the whole
  rule off for non-casters). **Absent = prepared**, or every existing caster would fall silent
  on updating (invariant 8, pinned by `checkPreparedSpells`). The limit is enforced by the server.
  **"Not prepared" and "cannot be cast" are not the same question**, and confusing them already broke the
  staff once: `/dndspells staff` casts by design a spell its bearer never learned, so it
  is not on their sheet and `isPrepared` returned false. The guard asks `preparationAllows` — the
  list only rules over what the sheet DOES know.
- **Grimoire v2** — sections by level with `addHeader`, and **the school and the "unprepared" go inside
  each row's label** instead of in filter buttons: `ListPickerScreen`'s automatic search box
  already filters by the label text, so typing "evoc" filters by school
  for free. Zero new widgets for that.
- **Network: zero new classes.** Preparing/unpreparing are two constants at the end of
  `BrowseActionMessage.Action` (invariants 2 and 3), with the spell id in the free-text field that
  already existed. `PROTOCOL_VERSION` 23, `NETWORK_SHAPE` 114, `NETWORK_ORDER` 1236403559.

**Skipped on purpose** (add when someone asks for it while playing, not before): a projectile entity with
its own physics (the die decides the hit, not the aim — the trail illustrates the rule instead of competing
with it), `DeferredRegister<ParticleType>` and own `.ogg` files, a radial spell wheel (none of the
four bases of invariant 7 supports it; the `R` quick-cast key covers the use), a favorites list
on the sheet, and a per-spell `description` field (the compendium already composes the description from
the stats). **And the "you can only recompose prepared spells after a long rest" lock: it is not
in place.** You can prepare and unprepare at any time; the limit is always respected.

## Architecture and the patterns worth reusing

**Content registries** (weapons, spells, monsters, presets, traits, feats) share one shape: an
in-memory map (`NamedRegistry<T>`) loaded from a JSON array via `JsonRegistryLoader<T>` (per-element
error isolation). `Config` (weapons) predates this and still hand-rolls its own maps — a known
inconsistency, not worth unifying alone. Race/background/class options (`CharacterOptionsRegistry`)
*replace* the whole category on load rather than merging by id, because there's no id, just a flat
string list.

**`DndPaths`** owns every `<world>/dndsheets/<type>/` folder and auto-loads every `.json` file found.
**Load order is `mod_defaults.json` first, then everything else by name**, and `NamedRegistry.register`
overwrites by id — a DM's file always wins over what the mod ships, which is what makes rewriting
`mod_defaults.json` on every start safe.

**The in-game content creator** (`ContentType` + `ContentPackFile` + `ContentFormScreen`):
`ContentType` wraps each id-keyed type's `load`/`remove`. `ContentPackFile` read-modify-writes a
dedicated `dm_created.json` per type, then re-invokes the type's normal `loadFile` — no separate
persistence layer. `ContentFormScreen` is a generic data-driven form for the flat-schema types;
traits/monsters/options get bespoke screens because their shape genuinely differs.

**GUI architecture**: three real `AbstractContainerScreen`s (character sheet, roll editor, advanced
roll editor); everything else is a plain `Screen` opened via a static `open(...)`, built on the four
bases in invariant 7. `GuiStyle` is the single source of the shared panel look; `TomeButton` is the standard
row; `CommandListScreen` is the generic list whose rows fire a chat command (a cheap GUI path
for any existing command — the permission stays on the command). The HUD hosts three
overlays with the same tome look: `TurnHudOverlay` (initiative board + action economy,
combat only), `ResourceHudOverlay` (resources/states, always) and `CombatLogOverlay` (the latest
combat lines, ephemeral — fed by recognizing the `chat.dndsheets.tag.*` labels of
`ChatFeedback` on the client, with no network of its own).

**Networking**: every message is a small hand-written class registered once in
`DndsheetsMod.registerNetworkMessages` (alphabetical, message id = registration order — invariant 1;
`PROTOCOL_VERSION` makes a client/server mismatch fail clean). `DndsheetsMod.withDmTarget` is the
shared op-check + target-resolution helper for DM-acts-on-another-player messages. Bulk "give one of
N similar things" actions use one message parameterized by an enum/type field (invariant 3).

**Sheet persistence**: `SheetLoader` keeps every character's sheet as an in-memory `JsonObject`,
backed by one JSON file under `<server>/charactersheets/`. The single write path is
`SheetLoader.saveServer` (invariant 4) — DM-initiated edits relying on the 5-minute autosave instead
was a real, since-fixed bug (bug #5).

**Dungeon generation** now lives in the `dungeon` addon: `DungeonPieceRegistry` (per-world) holds
captured pieces, `DungeonManager` converts them into vanilla `template_pool` datapack JSON and calls
`JigsawPlacement.generateJigsaw`. Most vanilla-API sharp edges in the project live here — see bugs
#7-#11 and invariants 5/6 before assuming `/reload` or a captured piece is trustworthy.

## The VTT roadmap and why it is in this order

Goal: a VTT competing with Roll20/Foundry/TaleSpire/Owlbear. The gap was never code quality — it was
scope, and three measured structural defects. Order is forced by dependencies, not preference.

- **Fase 0 — `Combatant` + conditions. DONE.** Without it every rule is written three times.
- **Fase 1 — character identity. DONE, GUI included.** Characters keyed independently of players;
  `/dndchar list|new|switch|npc|spawn`. `TurnManager.isMonster` (drives end-of-combat) is deliberately
  separate from `isCombatTarget` (a valid 5e target) — merging them would mean a friendly NPC in the
  room keeps combat from ever ending.
- **Fase 2 — SRD content. Imported in four batches; the bestiary is done.** 87 spells, 330 monsters,
  362 magic items (145 with resistances) from SRD 5.1, CC-BY-4.0 (see Attribution below). Sequencing
  after Fase 0 was load-bearing: the first batch alone found that damage was mandatory (blocking
  no-damage spells) and only applied `if (finalDamage > 0)` (imposing conditions on targets who
  **passed** their save).

  **The engine backlog this unlocked, all DONE:** area shapes (line/cone, originating at the caster
  along its view vector, not a radius — a flattened cone would hit the caster's own party); walls as
  persistent regions (damage whoever *starts their turn* inside, horizontal-only distance so standing
  on top doesn't burn); temporary HP + weapon buffs (`Combatant.takeDamage`
  default method, `absorbWithTemporaryHp` for the one PvP path that can't use it); summons that act on
  later turns (targeting had to exclude the summoner, and a summon must not count as an enemy or
  combat never ends); multi-round zones (`ZoneManager` — shape as a field, persistence
  (`mode: "zone"`) as its own field rather than inferred; absorbed the earlier `WallManager`, which
  no longer exists as a class); magic items (**the
  SRD publishes them as prose only** — reference half fully automatic, mechanical half derived from
  a second-person subject ("**you** gain...") and reviewed, 80 of 362 mechanical; potions are
  consumables, not passive, since their effect comes from drinking; Curios is a soft dependency for
  real ring/charm slots, attunement standing in for "worn" without it).

- **Fase 3 — the table layer. DONE.** Searchable compendium (`/dndcompendium`) for 779 entries;
  journal + handouts turned out to be one mechanism (title/body/visibility) rather than two, verified
  before writing. Visibility is filtered **server-side**, never on the client. Both ride the existing
  `Browse*` message pair — no new network message.

- **Fase 4 — progression fidelity. DONE.** See "Bugs fixed — condensed log" List B above; that whole
  list is Fase 4.

- **Fase 5 — the table you can actually sit down at. Items 2-4 and 6 done; 1 is the modpack, 5 is out
  of scope.** Ordered by how many people are lost at each step, not by how interesting the step is.

  1. **Getting in has to be one click** (not built) — a published Modrinth/CurseForge modpack pinning
     Forge + this mod + optional soft-deps, not an installer of our own.
  2. **Creating a character, not levelling one — done.** Starting gear per preset (barbarian/monk get
     none, on purpose — unarmoured defence *is* their class feature); skill proficiencies write
     `+ $prof` into the roll expression as an added/removed term, never a rebuild (would erase a
     manual edit); `CharacterSetupScreen` is a checklist of 4 existing screens, not a wizard, so a
     table can still fill a sheet in its own order; subclasses live inside their preset (a subclass
     without its class means nothing), grant exactly what a preset grants, gate the level **on the
     server**; feats spend the same pending Ability Score Improvement (two resources would defeat the
     point of a feat), only Grappler ships from SRD 5.1; multiclass enters as an optional field that
     wins when present (an unset sheet behaves exactly as before), with the two *different* rounding
     rules kept separate (single-class half-caster rounds up, multiclassed contributes half rounded
     down) and Warlock levels deliberately excluded from the caster-level sum (Pact Magic is a second
     pool this sheet can't carry).
  3. **The DM's prep loop — done.** Encounters (`EncounterRegistry`, text composition `"id xN"`,
     spawn in a ring not a stack) add no new rule — initiative already auto-starts on first hit.
     Imported builds: any `.nbt` (no `.schem`/`.litematic` converter — that's what the structure block
     already exports to) pastes or registers as a piece directly; import refuses outright when a pool
     is requested and the structure has zero jigsaws, rather than failing silently at generation time.
  4. **Light and vision — done** (`Light`, `VisionManager`, `/dndvision`, off by default). Adds no new
     condition — below light level 4 is just `Condition.CEGADO`, thresholds are vanilla's own light
     levels. Darkvision comes from race (`CharacterRules.darkvisionFeetFor`) with a `-1` sentinel
     override to explicitly remove it.
  5. **Positional voice — out of scope, by decision.** Simple Voice Chat already does this; an
     integration would buy a soft dependency for what two mods already do side by side.
  6. **SRD 5.2 importer + community JSON — done** (`tools/import_srd.py`). Detects 5e-bits, Open5e, or
     this mod's own schema from the first record; `--into` splices new entries as text rather than
     `json.dump`-ing the file (would reflow hand-written entries, invariant 10); `DamageTypes.normalize`
     fixed a real bug the importer exposed — an English-language pack's damage type never matched a
     Spanish sheet's resistance key. SRD 5.2 is where the other 15 feats (origin feats, fighting
     styles, Epic Boons) came from — 5.1 shipped exactly one.

  **Still out of scope:** fog of war, a token layer, the mod's own creature models, a web client,
  other tabletop systems — the 3D map, real line of sight and real lighting are native here, which is
  what the competition emulates with polygons and fog layers. Do not build a fog-of-war system.

## Roadmap 2026-08+ — from a complete mod to a product

### R4 — Distribution (the old Phase 5.1, the only item of the old roadmap still open)

A modpack published on Modrinth: Forge 47.x + core + addons + Origins/Apoli + optional soft-deps
(Curios, Patchouli, Jade, Pehkui) + the creature mods chosen for the appearance packs.
`tools/preflight_mods.py` is the basis of the server install docs.
Timing: AFTER R1 — publishing before fixing the first impression burns the launch.
`PROTOCOL_VERSION` 22 already breaks cleanly with any earlier build, so the first publication
drags no compatibility along.

⚠️ **`publishMod` can say `BUILD SUCCESSFUL` with a failed upload inside.** It really happened: with
an invalid slug in the relations, the output carries "Failed to Upload artifact to CurseForge" and the task
still ends successfully. The same if a token is missing (that is why the `checkPublishSecrets` guard exists).
**Read the output, not the exit code**: there must be a "Successfully uploaded" per platform. If
one of the two already uploaded and the other didn't, retry only the one that failed with `publishCurseforge` /
`publishModrinth` — repeating `publishMod` would duplicate the one that was already there.

**Uploading is already automated, to BOTH platforms:** `./gradlew publishMod` (the ModPublisher plugin,
see the `publisher {}` block of `build.gradle`). Tokens in `CURSE_TOKEN`/`MODRINTH_TOKEN` or in
`curseforgeToken`/`modrinthToken` of YOUR `~/.gradle/gradle.properties` — never in the repo. No normal
build depends on that task.

**Optional dependencies are declared in the build, not by hand on the web.** On CurseForge
relations are **per file**: every upload goes out with none unless they are set again, and the first
time it is forgotten nobody will notice. That is why they live in `curseDepends`/`modrinthDepends` of the
`publisher {}` block.

**The rule, which is what keeps that list from turning into noise: what is declared is what the project
REFERENCES, not what is recommended to install.** A relation on the page says "this mod talks to that
other one"; a table recommendation is something else and lives further below, in the list of companion mods. 11
remain: the 4 real integrations (Curios, Patchouli, Jade, Pehkui — the ones in `mods.toml` with
`mandatory=false` that have their own `*Compat` class) and the 7 appearance packs, which **are not a preference**
but exactly the modids that the `dndsheets/skins/` JSONs reference (`iceandfire`, `alexsmobs`,
`naturalist`, `twilightforest`, `mowziesmobs`, `guardvillagers`, `cataclysm`): if a
pack is added or removed, that list changes with it.

Left **out** by that rule, and the code itself says so: **Tinkers' Construct** (`Config.java` — other
mods' weapons work "without this mod having to know anything about Tinkers' Construct or any
other"), **EasyNPC** (`MonsterCommand.java` — "there is no EasyNPC integration or dependency on anyone"),
**AttributeFix** (zero mentions in the repo) and the three table recommendations (Configured, Customizable
Player Models, Dynamic Lights [Server]).

Two slugs that cannot be shared between platforms, and assuming otherwise cost a rejected
upload (CurseForge, error 1018): **Cataclysm changes name** — `lendercataclysm` on CurseForge,
`l_enders-cataclysm` on Modrinth — and **the Twilight Forest doesn't exist on Modrinth**, only on CurseForge.

⚠️ **The two addons cannot be published yet.** `dungeon/build.gradle` and `species/build.gradle`
produce their jar (`dndsheets-dungeon-1.0.0.jar`, `dndsheets-species-1.0.0.jar`) but **have no
`publisher` block**: today there is no way to upload them, so the dungeon toolkit and the race bridge
reach nobody even though the core does. And their dependencies **are not optional like the core's, they are
mandatory** (`mandatory=true` in their `mods.toml`): `dungeon` requires the core `[2.2.0,)`, and `species`
requires the core **and Origins `[1.10.0,)`** — they must be declared with `required(...)`, not `optional(...)`,
or someone will install `species` without Origins and it won't start. Apoli isn't declared: it travels inside
Origins' jar (see Library Audit). The real blocker: each addon needs its **own project** on CurseForge
and on Modrinth, and neither exists. A minor note for when it is done: their `archivesBaseName` still says
`dndsheets-*` even though their `displayName` is already "VTT MineRPG: …".

**There is no "syncing" CurseForge and Modrinth**, and it is best not to chase it: neither platform imports
the other's project. Description, images, categories and version history don't travel; the Modrinth page
is written once by hand and starts with 0 downloads. The only thing shared is the upload: the
same jar and the same version number to both at once.

**Published identity, already aligned with the repo.** CurseForge **1634980**, Modrinth **rESHXYW7**, name
**VTT MineRPG**, version **2.2.1** (the last file published before was `VTTMinecraft 2.1.1.jar`,
21-08-2026). The jar comes out as `vttminerpg-2.2.1.jar`.

⚠️ **The visible name changed; the `modId` did NOT, and must not.** It is still `dndsheets`, and from it hang the
already-saved sheets, the content ids (`dndsheets:goblin`), all the language keys
(`gui.dndsheets.*`), the datapack namespace and the two addons' dependencies. Renaming it
is not a rename, it is a user-data migration. What was renamed: the three `displayName`s
of `mods.toml`, `archivesBaseName`, and the three visible language strings (Guide title, creative
tab, key category) in `en_us`/`es_es` + the 6 regional copies via `sync_lang_variants.py`.

The version number lives in **a single place**, `version` in `build.gradle`: `mods.toml` uses
`${file.jarVersion}` (which Forge resolves from the manifest's `Implementation-Version`, set on
`jar`/`shadowJar`) and `preflight_mods.py` reads it from there. The addons' `versionRange="[2.2.0,)"` are
something else: the core floor they require, not their own version.

**Why the wrapper is Gradle 8.8 and not 8.1.1:** this forced it. 8.1.1's ASM can't read Java 21
classes, and ModPublisher drags in a `jackson-core` that ships them in `META-INF/versions/21/`; the build
didn't even evaluate. It is not a problem of that particular plugin —none of its published versions
predates that jackson— but of 8.1.1 falling out of the plugin ecosystem. With 8.8:
`build`, the self-tests and `runGameTestServer` pass just the same, and ForgeGradle 6.0.54 didn't flinch.

**Companion mods that are NOT dependencies and are worth having in the modpack** (zero code, zero
integration: the mod doesn't name them anywhere):

- **Dynamic Lights \[Server\] (Tschipcraft)** — the most important of the four, and the only one that
  *fixes a rule*. `VisionManager` reads the server's real light (`getMaxLocalRawBrightness`), so
  today a player with a torch in hand inside a cave is still in `DARK` and ends up **blinded
  by our own rule**. That mod plants real `light` blocks, server-side, and the number
  changes on its own. Client-side dynamic lights (LambDynamicLights, Dynamic Lights Reforged) **don't

  standing inside the region when scanning. Scanning from outside avoids it.
- **Easy NPC** — NPCs with dialogue, poses and skins. **It already fits without writing anything**: this

  `applyStatBlock` and the block's `keepsOwnAi` field say.
- **Configured** (or Forge Config Screens) — an in-game config screen for any
  `ForgeConfigSpec`. `Config` is 604 lines that today are edited in a TOML by hand.
- **Customizable Player Models** — the *player's* look. `MonsterSkins` resolves the monsters;
  the player's tiefling is still Steve. It stores the model in the skin itself: it doesn't even need

## Portability to future Minecraft versions

Targets **1.20.1/Forge**; the door to a future version is deliberately left open — a statement about
coupling, not a promised date.

**What already makes it cheap:** zero mixins, zero access transformers, zero reflection into vanilla
internals — Forge events and public API throughout. The 5e rules live in pure classes untouched by
Minecraft (`CharacterRules`, `SpellSlots`, `Cover`, `Condition`, `AttackRules`/`SaveRules`,
`CreatureType`) and already run outside a Forge runtime. All content is JSON and crosses unchanged.

**What the port actually costs, largest first:**
1. **Networking** — 64+ message classes on `SimpleChannel`, becomes the NeoForge payload API from
   1.20.5. Mechanical but bulky; invariants 1/2 matter *more* during a bulk rewrite, not less.
2. **Item NBT → data components (1.20.5+)** — small because it was kept small: everything this mod
   writes onto an item lives in one compound (`dndsheets`), so it's one migration, not one per item
   kind.
3. **Metadata/toolchain** — `mods.toml` → `neoforge.mods.toml`, Java 17 → 21, Parchment version.
4. **Worldgen/jigsaw** (now in the `dungeon` addon) — the area with the most vanilla sharp edges
   already (bugs #7-#11); assume the API moved and re-verify against decompiled source.

`versionRange="[1.20.1]"` stays strict on purpose — 1.20.2 changed networking and 1.20.5 changed item
data, so widening it would load the mod into a game where it can't work. `checkPortabilityCoupling`
asserts the absence of mixins/access-transformers and that item NBT stays touched only from the
annotated file set — it can't make the port cheaper, it stops the coupling from growing unnoticed
before someone does it.

## Where to go next

- Touching combat, damage, AC, hit points or conditions → go through `Combatant`. An `instanceof
  Player` branch to decide how to read a stat already has a home behind the interface.
- Adding a screen or touching layout → invariant 7: extend one of the four bases, never bare `Screen`.
- Adding a content type or command → check whether `ContentType`/`NamedRegistry`/`JsonRegistryLoader`
  already fits before writing a parallel pattern.
- Touching item NBT, or reaching for a mixin/access transformer → read "Portability" first;
  `checkPortabilityCoupling` fails the build rather than let one in unnoticed.
- Touching dungeons → they live in the `dungeon` addon now. The "golden rule" (invariant 6) and bugs
  #7-#11, before trusting `/reload` or a captured piece.
- Touching race/background/Origins → the `species` addon; Origins picks, this addon writes the sheet
  through the core's normal path — see "Modularity Map".
- Adding or evaluating a soft dependency → "Library Audit" for the compileOnly/isolation pattern and
  why it can't be tested in `runClient`.
- Adding a sound → "Attribution > Audio". CC0 only, mono (Minecraft plays a stereo `.ogg` WITHOUT
  direction), and its line in that list or `checkAudioAssets` fails the build. Referencing a vanilla `SoundEvents.*`
  costs no license at all and is still the default route: an own file is only shipped
  when vanilla has nothing that sounds like that.
- Anything DM-facing that hands out an item/teaches a spell/spawns a monster → there's almost
  certainly an existing `GiveableItem`-style pattern or DM Panel row to extend.
- How a monster looks → `MonsterRegistry.Appearance` (equipment, baby, glow) and `baseEntity`, which
  accepts the entity of any installed mod — the mod ships no models of its own. Check whether it draws
  its equipment and whether it acts on its own before picking one. Verified in `checkMonsterAppearance`.

### Audio

**Every sound track shipped in the jar is listed here, with its license.** It is not courtesy: it is the
condition for redistributing it, same as with the SRD. *Machine-enforced:* `JsonContentSelfTest.checkAudioAssets`
fails the build if an `.ogg` shows up in `assets/dndsheets/sounds/` that has no line in this list,
so deleting the entry breaks compilation instead of silently creating a legal problem.

The format of each line is read by the self-test: `` - `file.ogg` — LICENSE, origin.``

- `dice.ogg` — CC0 1.0, original work of the project. (stereo)

**CC0 only.** It is a decision, not what happened to be at hand: CC-BY would also allow redistribution, but
it forces keeping a per-file credits list alive, and an attribution nobody checks rots.
The SRD survives in this repo because there is a self-test that fails the build if the citation disappears; a CC-BY
without that same lock is a promise a refactor breaks six months later. CC0 doesn't create the problem.
Ruled out as incompatible with redistribution in a modpack (see R4): CC-BY-NC, Sampling+,
and Zapsplat-style libraries whose terms forbid redistributing the file as an asset.

**Mono, or there is no positional audio.** Minecraft plays a stereo `.ogg` without direction: a spell
would sound the same next to you as thirty blocks away. It is the classic trap and `checkAudioAssets` checks it by reading
the Vorbis identification header, so it doesn't depend on anyone remembering. The `(stereo)` mark
on the attribution line is the explicit exception — today only `dice.ogg` uses it, which came from the initial
commit (it was MCreator) at 24 kHz and two channels. Re-exporting it in mono from its original is a pending
improvement, not a regression: it is how it sounded from the start.

### How the import is reproduced

It is not prose, it is a command. The packs are regenerated with `tools/import_srd.py`, which reads the
JSON transcription of the SRD (5.1 or 5.2) and translates it into this mod's schemas:

```
python tools/import_srd.py --kind feat --from https://raw.githubusercontent.com/5e-bits/5e-database/main/src/2024/en/5e-SRD-Feats.json --lang tools/lang/srd52_feats_es.json --into src/main/resources/dndsheets/defaults/feats.json
```

The translations live in `tools/lang/` so the command can reproduce a localized file; the file that
ships is now the English one, so `--lang` is only needed for a Spanish variant. The same importer accepts [Open5e](https://open5e.com/) for
community **OGL** content — that material is NOT shipped with the mod; each table brings it into its world
under the license that applies to it.
